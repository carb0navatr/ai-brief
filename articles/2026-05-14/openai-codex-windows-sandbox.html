OpenAI 为 Windows 版 Codex 构建安全沙箱：让 AI 编程助手在 Windows 上既高效又安全

原文要点

OpenAI 工程团队在 2026 年 5 月 13 日详细披露了其为 Windows 版 Codex（OpenAI 的 AI 编程助手）构建自定义沙箱的技术历程。

核心问题：此前 Windows 用户只能在两种糟糕的方案中二选一——要么频繁批准几乎所有操作（效率极低），要么开启"完全访问"模式（安全隐患极大）。

技术方案：团队依次评估了 Windows 原生的三种隔离机制——AppContainer（过于狭义，不适合开放性开发者工作流）、Windows Sandbox（需要单独的虚拟机，无法直接操作用户实际环境，且 Home 版 Windows 不支持）和 MIC 完整性标签（会修改真实文件系统语义，风险过高）。最终，团队设计了自己的沙箱方案。

最终实现（"提升权限沙箱"）：

  • Codex 运行时创建两个专属本地用户：CodexSandboxOffline（被防火墙规则限制网络访问）和 CodexSandboxOnline（不受限）
  • 命令以写受限令牌（write-restricted token）运行，限制文件系统写入范围
  • 通过 SID（安全标识符）+ ACL 精确控制可写目录
  • 依赖 Windows 防火墙阻断出站网络流量

该方案需要在设置时拥有管理员权限，但运行时的网络保护比初代"非提升"原型强得多。

为何重要

1. Windows 开发者安全体验终于对齐 macOS/Linux

Codex 在 macOS 上有 Seatbelt、在 Linux 上有 seccomp/bubblewrap，都可直接调用系统级隔离能力。Windows 原生缺少同类工具，导致长年以来 Windows 用户要么安全妥协、要么体验妥协。此次披露标志着 Windows 开发者终于获得了与 macOS/Linux 用户同等安全保障的可能。

2. 揭示了 AI Agent 安全落地的真实工程复杂度

这篇文章罕见地展示了 AI Agent 产品化过程中"安全 vs. 体验"权衡的完整思维链条：从评估现有工具的失败、到第一代方案的取舍、再到最终方案的技术决策。这种公开透明有助于整个行业理解在生产力工具中嵌入 AI 的工程挑战。

3. 对企业安全团队有直接参考价值

Codex 的沙箱设计展示了如何用 Windows 原生机制（SID、ACL、写受限令牌、Windows 防火墙）组合出企业级隔离方案。任何在 Windows 环境中运行第三方 AI 工具的企业，都可以参考这一架构来设计自己的边界控制。
