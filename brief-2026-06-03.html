基础设施

1. NVIDIA 与微软联合发布统一技术栈，瞄准 Agentic AI 时代

NVIDIA 与微软在 Microsoft Build 大会上宣布了深度合作，旨在为 Agentic AI 构建从 Windows 设备到 Azure 云再到本地部署的完整全栈方案。核心发布包括：

  • NVIDIA RTX Spark：全球首款专为 AI 代理原生设计的 Windows PC，搭载于笔记本电脑和小尺寸台式机，为本地 AI 代理提供加速算力。

  • DGX Station for Windows：面向企业桌面的 AI 超级计算机，将万亿参数级 AI 能力直接带到每个企业员工的桌面。

  • Microsoft Fabric 加速：NVIDIA GPU 加速的 Microsoft Fabric 数据分析平台，集成 NVIDIA 开放模型于 Microsoft Foundry。

  • NVIDIA OpenShell：安全的 AI 运行时，已整合进 GitHub Copilot，提供沙箱隔离与策略执行能力。

  • 下一代 AI 工厂：黄仁勋（Jensen Huang）在 Build 主题演讲中与微软 CEO 纳德拉（Satya Nadella）共同阐述双方在 AI 工厂基础设施上的合作规划。

关键合作背景：黄仁勋从台北 COMPUTEX 会场远程参加了微软 Build 的主题演讲，凸显了两大生态系统的深度联动。

这次合作代表了 AI 基础设施竞争格局的一次重要演变：不是单纯的模型性能竞争，而是全栈控制权的争夺。

对于企业而言，这意味着几个深刻变化：

  1. AI 代理终于有了原生操作系统层面的支持。过去企业部署 AI 代理需要自己拼凑安全、运行时和基础设施方案；现在 NVIDIA + 微软的组合提供了从芯片到云到桌面的完整路径，降低了企业采纳门槛。

  2. 本地化推理能力真正进入企业视野。RTX Spark 和 DGX Station for Windows 让企业可以在本地运行大规模 AI 代理，不必把所有数据都送到云端，这对于金融、医疗等强监管行业意义重大。

  3. OpenShell 的意义被低估。AI 代理的安全治理一直是企业大规模部署的最大阻力——OpenShell 作为开放的沙箱运行时，并与 GitHub Copilot 深度集成，可能成为企业级 AI 代理安全标准的雏形。

  4. 这不是单一产品的发布，而是生态锁定。当企业同时使用 RTX Spark（硬件）+ DGX Station（算力）+ Microsoft Fabric（数据）+ Azure（云端）+ OpenShell（安全）时，切换成本将极高。

  • NVIDIA 与微软的合作伙伴关系覆盖了从设备端（RTX Spark）到桌面端（DGX Station）到云端（Azure）的完整 AI 代理基础设施

  • OpenShell 安全运行时已进入 GitHub Copilot，为 AI 代理提供企业级沙箱和策略控制能力

  • 本地 AI 推理不再是实验性功能，正在成为企业 AI 战略的正式组成部分

  • 黄仁勋与纳德拉的同台体现了 AI 工厂（AI Factory）作为下一代企业基础设施的核心定位

2. NVIDIA Computex 2026 企业 AI 代理公告：消费硬件背后被忽视的企业级机会

Beam AI 对 NVIDIA Computex 2026 发布的六项 AI 代理产品进行了企业视角的深度解读，认为大多数媒体聚焦于 RTX Spark 笔记本电脑芯片，而三项企业级公告对实际部署 AI 代理的团队影响更大：

1. Vera CPU — 专为 Agentic AI 和强化学习工作负载设计的数据中心处理器，相比传统 x86 服务器 CPU 声称效率提升 2 倍、性能快 50%。早期客户包括 OpenAI、Anthropic 和 SpaceX。

2. Nemotron 3 Ultra — NVIDIA 新款开源权重模型：5000 亿参数（MoE 架构，每个 token 约 500 亿参数活跃），输出速度超过每秒 300 个 token（比同类前沿模型快 5 倍），运行成本降低约 30%。专门针对多步推理、长时任务规划和自纠正等代理核心能力进行调优。提供开源权重和训练配方，支持企业基于自有数据微调。

3. NeMoClaw — 编排框架，提供 AI 代理规划、推理、执行和委托的蓝图模板。相当于替代企业从零编写 ReAct 循环和工具调用链路的方案。内置常见企业模式模板：任务分解、多代理委托、带错误恢复的工具调用。

4. OpenShell — 安全和治理层，提供沙箱运行时，企业可定义代理的权限边界和需要人工审批的操作。通过与微软的合作将进入 Windows，但企业服务器部署意义更大。

  1. Nemotron 3 Ultra 是开源 LLM 竞争格局的重要变量。5000 亿参数 + 每秒 300 token + 比前沿模型快 5 倍 + 成本降低 30%，将对 Mistral、Llama 和 Qwen 系列构成直接竞争压力。企业用户获得了在自有基础设施上运行高性能开源代理模型的选择。

  2. NeMoClaw 解决了企业代理落地的"最后一公里"问题。大多数企业构建 AI 代理时最耗时的不是模型选择，而是编排逻辑设计。NeMoClaw 作为"蓝图画廊"的价值是降低企业工程成本的标准化起点。

  3. OpenShell 是企业代理安全领域的"缺失环节"。构建一个能干的代理很容易，构建一个满足合规团队要求的企业级安全代理非常困难。OpenShell 的存在意味着 NVIDIA 不仅在提供模型，还在提供企业采纳所需的安全治理框架。

  4. Vera CPU 面向的是"代理工厂"场景。OpenAI、Anthropic 和 SpaceX 已成为 Vera 的早期用户，说明这款芯片的目标场景是运行数以千计并发代理会话的数据中心。

  • Nemotron 3 Ultra（5000 亿参数开源模型）将推理速度提升 5 倍、成本降低 30%，为企业在自有基础设施上运行高性能代理模型提供了新选择

  • NeMoClaw 编排框架通过预制蓝图降低企业构建 AI 代理的工程复杂度

  • OpenShell 作为企业级安全运行时填补了代理安全治理的行业空白

  • Vera CPU 面向"代理工厂"数据中心场景，OpenAI、Anthropic、SpaceX 为早期客户

4. Microsoft Build 2026：Windows 正在成为 AI 代理的操作系统

Microsoft Build 2026 的 Windows 开发者发布集中体现了微软的平台战略转向：将 Windows 打造成 AI 代理的原生操作系统：

  • Windows Development Skills 正式发布（GA）：让 AI 代理能够利用结构化知识完成原生 Windows 应用完整开发生命周期，支持 WinUI 3 和 WinApp 命令行工具。

  • Intelligent Terminal 0.1（实验性）：开源的 Windows Terminal 分支，内置代理集成，支持 Agent Client Protocol 兼容代理。

  • Microsoft Execution Containers（MXC，早期预览）：政策驱动的 AI 代理沙箱执行层，支持进程隔离和会话隔离，GitHub Copilot CLI 已采用 MXC 进程隔离。

  • Windows 365 for Agents：将 Cloud PC 作为 AI 代理的执行层，适用于无可靠 API 的桌面/Web 应用交互、UI 级操作和人工审批工作流。

  • Aion 1.0 Plan 模型：140 亿参数推理和工具调用模型，支持本地运行完整代理工作流，将作为 Windows 选配功能随机器预装。

  • Project Solara：面向多代理时代的芯片到云平台，展示未来代理优先体验。

这是微软在 AI 时代最清晰的一次平台战略表态：

  1. 从"AI in Windows"到"AI as Windows"——Build 2026 的主题是让 AI 代理成为 Windows 的核心功能单元，而非应用层面的附加。

  2. MXC 的战略意义可能被低估。AI 代理安全治理是整个行业最大的痛点之一——微软选择通过 Windows 操作系统级别来强制执行沙箱策略，这是苹果的 App Sandbox 在移动端开创的模式在 AI 时代的复刻。如果 MXC 能建立行业标准，微软将在企业 AI 代理安全领域占据类似其在企业操作系统市场的地位。

  3. Aion 1.0 的本地化推理战略。将 140 亿参数模型直接预装在 Windows 设备上，是微软对"AI 时代设备差异化"的核心押注——让设备本身成为 AI 代理的天然运行载体。

  4. Project Solara 意味着微软已经不再将 AI 代理视为单一软件功能，而是开始思考"代理优先"的芯片到云完整平台。

  • Windows 正在从 AI 工具的承载平台升级为 AI 代理的原生执行环境

  • MXC（Microsoft Execution Containers）通过 OS 级别沙箱解决 AI 代理安全治理问题，GitHub Copilot CLI 已采用

  • Windows 365 for Agents 将 Cloud PC 定义为 AI 代理的正式执行环境

  • Aion 1.0 Plan（140 亿参数本地模型）使设备本身成为 AI 代理的运行载体

  • Build 2026 的核心叙事是"平台就绪"，而非"模型更强"——微软在争夺 Agentic AI 时代的基础设施定义权

6. GitHub Copilot 全面转向用量计费：企业如何应对成本新范式

GitHub 于 2026 年 6 月 1 日正式将所有 Copilot 计划的计费模式迁移至用量计费（Usage-based Billing）：

  • 用量计费全面生效：各计划提供每月包含的 AI Credits 用量；超出部分可继续消费并按月结算账单。

  • Copilot 代码审查消耗 Actions 分钟数：Copilot Code Review 现在同时消耗 Actions 分钟数和 GitHub AI Credits，组织管理员可设置默认运行器统一管理。

  • 用户级预算（User-level Budgets）正式发布：面向组织和企业的细粒度支出管控功能，管理员可设置通用预算或针对特定用户组设置覆盖预算。

  • Copilot Max 面向高强度用户开放：面向现有 Student、Pro 和 Pro+ 订阅者的升级选项。新用户注册仍暂停，预计未来数周重新开放。

GitHub Copilot 的用量计费转型是 AI 编程工具商业化的一次关键节点：

  1. "按效果付费"时代的加速到来。固定月费的逻辑是"用多用少一个价"，用量计费则是"用多少付多少"。高频用户可能面临成本大幅上升。

  2. 企业成本管控成为新的采购决策维度。用户级预算功能直接回应了企业 CFO 的核心关切——AI 工具的不可预测性支出。

  3. 代码审查的计费逻辑变化值得关注。Copilot Code Review 同时消耗 Actions 分钟数，意味着企业现有的 CI/CD 成本结构将被打破。

  4. 新用户注册的持续暂停说明 GitHub 仍在解决容量或成本问题。

  • GitHub Copilot 全面转向用量计费模式，固定订阅时代结束

  • Copilot Code Review 现同时消耗 Actions 分钟数，企业 CI/CD 成本结构面临重塑

  • 用户级预算功能正式发布，为企业提供细粒度的 AI 工具成本管控能力

  • Copilot Max 开放升级，面向高频使用场景提供更高包含用量

7. Salesforce Summer '26 发布：Agentforce 多代理编排将"代理化企业"推向现实

Salesforce 于 2026 年 6 月 15 日发布 Summer '26 版本，将"代理化企业"（Agentic Enterprise）愿景落到实处：

  • Agentforce 多代理编排正式发布：多个 AI 代理作为统一团队协作解决复杂端到端工作流，客户获得单一联系点，所有渠道共享上下文。

  • IT 服务领域包增强：在 Slack、Teams 和 IT Service Desk 中部署超过 50 个开箱即用的专业 AI 代理，主动检测意图并在各专业角色间主动解决员工需求。

  • Tableau MCP（Model Context Protocol）：让 AI 代理直接查询 Tableau 分析引擎，在业务上下文中有据可查地提供准确答案，Agentforce Trust Layer 保护数据安全。

  • Agentforce 自助服务重新设计：新 Help Agent 可在 6 次点击内完成配置。

  • Slack 优先的代理工作流：所有代理能力深度嵌入 Slack，代理可以在对话中直接执行任务并汇报结果。

  • 实时数据激活：通过 Salesforce Data Cloud 实现跨数据源的实时数据整合。

Salesforce Summer '26 是目前为止最完整的企业级多代理平台发布之一：

  1. 多代理编排的"单一联系点"设计是正确的产品思路。企业部署多个 AI 代理后面临的最大问题是"客户不知道该找哪个代理"——Salesforce 通过统一的入口和共享上下文解决了这个问题。

  2. Tableau MCP 的意义超越了数据集成本身。当 AI 代理可以实时查询 Tableau 的分析引擎时，它实际上成为了一家企业的"数据代理"——将 AI 代理从"信息查找工具"升级为"数据决策支持系统"。

  3. 50 个开箱即用的 IT 领域代理是一个大胆的规模化策略。这与微软 Scout 的"用户自建"路径形成了鲜明对比——Salesforce 押注的是"开箱即用的代理即产品"。

  4. Trust Layer 是企业合规的关键保障。Agentforce Trust Layer 的存在是大型企业采购决策的必要条件。

  • Agentforce 多代理编排将多个 AI 代理整合为统一团队，客户获得单一入口和共享上下文
